## Why a reset confirmation can appear without an email

The browser calls Supabase Auth’s recovery API. To avoid disclosing whether an account exists, the page always returns the same confirmation. Delivery errors now produce a sanitized `auth_recovery_request_failed` diagnostic; addresses, passwords, bodies, tokens and raw provider errors are excluded.

Vercel’s `RESEND_API_KEY` does not configure Supabase Auth. The reviewed `/api/auth/send-email` HTTP hook must be deployed, its signing secret set in Vercel and the hook enabled in the selected Supabase project. Until that is done, Supabase continues using its own configured mail path. The actual production cause requires the Auth delivery log for a failed request; local code inspection alone cannot establish it.

## Assisted recovery

1. Developer or actual Super Admin opens **Account Recovery** from navigation or Developer Tools. Role previews cannot issue recovery links. Ordinary administrators, Finance and Staff cannot issue them.
2. Verify the employee’s identity using the organization’s approved process. Select an active, verified CAEDM employee with completed onboarding. Self, Super Admin, active Developer, pinned protected and enrolled-MFA targets require IT recovery instead.
3. Confirm identity, enter the operator’s current password and enrolled/required authenticator code. An isolated Auth session verifies the operator; the browser identity remains unchanged. PostgreSQL independently checks role/designation, preview state, fresh password AMR and MFA policy.
4. Preparing a link immediately restricts the target’s workspace permissions. Auth Admin `generateLink` is used only after the signed-in fresh-auth RPC returns the exact authorized target. It does not send email, create a user, confirm an address or assign a role. This is a narrow administrator-controlled authentication recovery operation; service credentials never query business tables.
5. The server emails the one-time link directly to the bound employee's verified work address. Never put it in tickets, audit detail, application logs or shared channels. The link contains an independent random 256-bit application code; only its fingerprint is retained. Supabase’s underlying recovery token is encrypted with AES-256-GCM and a purpose-derived server key, stored in a private RLS table and never sent to the browser. The application code is in the URL fragment, removed after browser ingestion and excluded from HTTP URLs and Referrer headers. It is submitted by POST only when the employee chooses a password. The operator receives an email acceptance/failure result, never the capability.
6. The employee chooses a new private password. The server validates the capability’s binding, 15-minute expiry, current issuer/target eligibility, then a narrowly scoped service-only recovery RPC checks those conditions again and leases the encrypted token for 30 seconds. It blocks concurrent redemption/reissue. Only the server decrypts and uses Supabase `verifyOtp` and `updateUser`. No administrator-selected or emailed password is used. The application code cannot be used directly at Supabase Auth to evade its application expiry. Rotating the server credential invalidates outstanding ciphertext; issue a new link afterward.
7. A tightly scoped Auth password-change trigger completes recovery. Workspace RLS rejects pending recovery and all sessions created before completion, including the recovery session. The employee must sign in with the new password. A password change through the ordinary valid email recovery path also completes pending assisted recovery.

Recovery never changes email verification, approval, role, department membership or financial records. Replacement invalidates the old application capability; Supabase’s one-use token adds a second boundary. Failed preparation/expired links leave workspace access restricted until a valid password change. Generate a replacement after one minute or use ordinary Forgot password. There is no “cancel and restore old sessions” bypass. Limit: five starts per operator per hour and one per target per minute. Append-only audit contains issuer/target IDs and actions, never tokens or passwords. Security notices use the existing protected account-email queue and do not depend on software reminder preferences.

Supabase session rows are read only to enforce the completion cutoff for recovered accounts; sessions belonging to other users are never impersonated. Database grants expose no recovery table or token digests. The anonymous validation RPC returns only the bound UUID for a valid high-entropy capability and reveals nothing for an invalid one. No MFA factor is removed or bypassed.

## Delivery policy and latency

- Set `EMAIL_PROVIDER=resend` and `RESEND_API_KEY`. A key selects Resend by default only when no provider is explicitly set; `EMAIL_PROVIDER=smtp` remains an intentional legacy rollback.
- `EMAIL_SMTP_FALLBACK=true` enables fallback when `SMTP_HOST` and the existing Exchange settings are present. `false` disables it. SMTP uses required STARTTLS on 587 or implicit TLS on 465, certificate verification and the configured authorized `EMAIL_FROM`; Resend uses the six purpose-specific CAEDM senders. Ask IT to maintain the fallback mailbox’s Send As permissions.
- Resend HTTPS avoids Exchange connection/TLS/authentication setup on successful primary sends. Existing process pacing and queue claims remain, rather than unbounded parallel sends that provoke quota failures. Fallback has a single remaining time budget including connection, greeting, socket and overall timeout, so an Exchange outage does not add another full unbounded wait.
- Fallback occurs only after explicit Resend rejection (400/401/403/422/429). Network timeouts, malformed successful responses, conflicts and server errors have an uncertain acceptance outcome, so they remain on Resend with the same idempotency key. Never race providers or blindly cross over after a timeout. Supabase Auth hooks have a five-second total budget; their smaller 1.8-second send budget also bounds fallback. A slow fallback fails cleanly rather than blocking Auth indefinitely.
- Worker activity records the actual accepting transport, not merely the configured primary. `smtp:` receipts cannot be mistaken for Resend delivery receipts. Provider acceptance does not prove inbox delivery. SMTP has no API idempotency or Resend delivery webhook: a lost SMTP acknowledgment/database finish can still require manual investigation before retry. This is an at-least-once boundary, not an exactly-once guarantee.
- API keys may be sending-only. A `/domains` read returning `restricted_api_key` does not prove the key is invalid. No live recipient is mailed as a configuration probe by this release.
